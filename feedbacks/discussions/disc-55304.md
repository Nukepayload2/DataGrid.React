# disc #55304 table 分页组件当前页码最大值取总页码不合理

## 现象
后端分页场景下，用户删除最后一页（N）的所有数据后，前端把 `pagination = { current: N+1, pageSize: 1, total: N }` 传回 antd Table。Table 内部 `usePagination` 会强制 `current = maxPage = ceil(total / pageSize)`，把当前页钳到 N —— 结果 N 这页码在分页条里被「自动选中」，用户**点不动**第 N 页，分页交互卡死。

## 复现 / 触发条件
1. 列表分页：`pageSize: 1`，`total: 40`，初始 `current: 41`（接口返回 —— 因为删了第 41 页数据）。
2. antd Table 内部源码（`components/table/hooks/usePagination.ts`）：
   ```ts
   const maxPage = Math.ceil((paginationTotal || total) / mergedPagination.pageSize!);
   if (mergedPagination.current! > maxPage) {
     mergedPagination.current = maxPage || 1;
   }
   ```
3. 钳到 40 后，分页器把 40 高亮为当前页，用户无法再点击 40 触发 onChange。

## 期望 vs 实际
- **期望**：Table 应在删除后**自动跳到上一页（maxPage - 1 或合适的上一页）**，或至少允许 onChange 重新触发到 maxPage。
- **实际**：源码只是把 current 同步成 maxPage，不触发 onChange，UI 直接显示「已选中 maxPage」状态，用户无法点击同页刷新。

## 根因 / 关键讨论
- OP 自答（贴源码）说明这是 antd 内部的 `usePagination` clamp 逻辑。
- 另一位回复者追问 `current: 41` 是否真的来自后端 —— 实际是用户业务层没正确同步，删除数据后业务代码应主动把 current 置为 maxPage。
- dosubot 给出官方立场："属于预期设计"，并给出 workaround：
  ```ts
  if (newTotal > 0 && newCurrent > Math.ceil(newTotal / pageSize)) {
    setPagination({ current: Math.ceil(newTotal / pageSize), pageSize, total: newTotal });
  } else if (newTotal === 0) {
    setPagination({ current: 1, pageSize, total: 0 });
  }
  ```
  即业务层在删除回调里手动修正 current。

## 对 data-grid 的启示
1. **clamp 的副作用**：data-grid 的 usePagination clamp 在静默修改 current 时，应**同时触发 onChange**（或至少提供 `onCurrentClamped` 回调），避免「UI 显示 maxPage 但用户点不动」的死锁状态。
2. **API 增强**：考虑提供 `pagination.autoFixCurrent: boolean | 'always' | 'only-after-delete'` 显式开关，让业务方选择是否自动修正；以及 `pagination.fallbackCurrent: (total, pageSize) => number`，让用户自定义删除后应跳到哪页。
3. **Demo 示例**：在「服务端分页 + 删除」示例里写一个回归用例：删最后一页 → 自动跳 maxPage 或 maxPage-1 → 用户应能再次点该页触发请求。
4. **文档警示**：明确写出「clamp 不触发 onChange」这一行为，避免业务方误以为 current 自动修正后内部也会重新拉数据。
5. 与 antd 一致的边界用例：`total = 0` 时 `current = 1`（避免 maxPage = 0 的极端）。
