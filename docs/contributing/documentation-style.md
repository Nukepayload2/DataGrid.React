# 文档风格

data-grid 的文档按“长期可读”组织，不再把任务编号、批次记录和返工过程保留在正文里。

## 总原则

- 写功能、设计原因、已知边界，不写会话进度。
- 文档标题按功能命名，不按字母批次、任务批次或文件所有权命名。
- 重要设计取舍进入 [`../decisions/`](../decisions)，不要只留在某个 demo 注释里。

## 功能文档写什么

每篇功能文档优先回答三件事:

1. 这个能力对外表现是什么
2. data-grid 为什么这样实现
3. 与 antd 或原生表格相比，哪里需要特别注意

## 源码注释迁移规则

- 源码里只保留短注释，说明局部特殊情况即可。
- 复杂推导、兼容差异、踩坑原因移到对应 `docs/features/**`。
- 注释里不要继续保留任务号、决策号、批次名或交接路径清单。

推荐格式:

```ts
// 简短标题 - 详见 docs/features/<domain>/<topic>.md
```

## 文档落点

- 架构层面的长期说明: `architecture/`
- 关键设计取舍: `decisions/`
- 功能行为和实现边界: `features/`
- 兼容矩阵、命名空间和限制清单: `reference/`
- 写作和验证规范: `contributing/`

## 不再保留的内容

- 任务拆批、进度状态、交接清单
- “之前是 X 现在改成 Y” 的历史叙事
- 与当前代码不符的旧实现描述
- 为 agent 流程写的调度说明
